# PawPath 백업 및 복구 정책

DB가 깨지거나 잘못된 작업으로 데이터를 잃었을 때 되돌리는 기준과 절차입니다. 구현은 `backend/app/services/backup_service.py`, 명령은 `backend/app/backup.py`입니다. 표준 라이브러리 `sqlite3`만 쓰고 외부 서비스는 쓰지 않습니다.

## 기준

| 항목 | 기준 | 비고 |
|---|---|---|
| 대상 | SQLite DB 전체 | PostgreSQL은 [아래](#postgresql) 참고 |
| 주기 | 24시간마다 자동 (`BACKUP_INTERVAL_HOURS`) | 서버가 1시간마다 확인. 꺼져 있던 동안 놓친 백업은 켜자마자 만듦 |
| 복구 시점 목표(RPO) | 최대 약 25시간 | 마지막 백업 뒤의 변경은 사라짐 |
| 복구 시간 목표(RTO) | 문제를 안 뒤 30분 이내 | 명령 자체는 수 초. 실제 장애로 측정한 값은 아님 |
| 보존 기간 | 14일 (`BACKUP_RETENTION_DAYS`) | 지나면 자동 삭제. 복구 전 DB 사본도 같음 |
| 위치 | `./backups` (`BACKUP_DIR`) | 기본값은 DB와 같은 디스크. [한계](#한계) 참고 |
| 접근 권한 | 파일 600, 폴더 700 | 비밀번호 해시, 경로, 사진이 들어 있음 |
| 훈련 | 실서비스로 열면 월 1회 복구 훈련 | 아래 절차를 임시 폴더에서 그대로 실행 |

300MB DB(사진 포함)에서 잰 시간입니다(개발용 Mac, SSD). 백업 0.80초, 검증 0.43초, 복구 1.65초.

## 들어 있는 것

| 백업에 있음 | 백업에 없음 |
|---|---|
| 보호자, 비밀번호 해시, 세션 해시 | `.env`: 비밀값이라 따로 안전하게 보관 |
| 반려동물, 추천, 산책 기록, 피드백 | 기기에 임시 저장한 산책 기록 |
| 산책길, GPS 지점, 사진, 내 코스, 커뮤니티 글 | 코드와 시드 코스: 저장소에 있음 |

## 백업이 만들어지는 방식

1. SQLite 온라인 백업으로 사본을 만듭니다. 서버가 쓰는 중이어도 커밋된 내용만 들어갑니다.
2. 사본의 무결성을 검사하고 SHA-256을 함께 저장합니다(`.sha256`, `shasum -c`로 확인 가능).
3. 검사를 통과한 사본만 `pawpath-날짜-시각.db` 이름을 받습니다. 중간에 멈추면 임시 파일만 남고, 하루 뒤 지워집니다.
4. 백업에 성공한 뒤에만 보존 기간이 지난 파일을 지웁니다.

자동 백업이 실패해도 서버는 계속 돌고 로그에 `자동 백업 실패`를 남깁니다. 끄려면 `BACKUP_ENABLED=false`입니다.

## 명령

`backend` 폴더에서 실행합니다.

```bash
uv run python -m app.backup create            # 지금 백업
uv run python -m app.backup list              # 목록
uv run python -m app.backup verify            # 가장 최근 백업 검증 (파일 이름도 가능)
uv run python -m app.backup restore latest    # 복구 (파일 이름도 가능. --yes면 확인을 묻지 않음)
uv run python -m app.backup migrate           # 마이그레이션 전 백업, DB 구조 올리기, 전후 행 수 비교
```

### 프로필 마이그레이션

대표 계정과 프로필을 더하면서 기존 DB에 `profiles` 테이블과 `profile_id` 컬럼이 생깁니다. 서버를 켜면 자동으로 진행하고, 미리 확인하려면 `migrate` 명령을 씁니다.

1. 바꿀 것이 있으면 먼저 `pre-migration-YYYYMMDD-HHMMSS.db`로 백업합니다(서버 자동 실행은 `BACKUP_ENABLED=true`일 때).
2. 빠진 컬럼과 색인을 더하고, 대표 프로필이 없는 계정마다 계정 이름과 일정으로 대표 프로필을 만듭니다.
3. 프로필이 비어 있는 산책 기록, 피드백, 추천, 나만의 산책길을 그 계정의 대표 프로필로 잇습니다. 산책길의 수정 시각은 바꾸지 않습니다.
4. 주요 테이블의 행 수를 전후로 비교해 줄어든 테이블이 있으면 실패로 알리고 복구할 백업 이름을 알려 줍니다.

프로필 잇기(2의 프로필 생성과 3)는 한 트랜잭션이라 중간에 실패하면 채우던 내용이 모두 되돌아갑니다. 먼저 더한 빈 컬럼은 남지만 데이터에 영향이 없고, 다시 실행하면 이어서 진행합니다. 비어 있는 행만 채우므로 여러 번 실행해도 프로필이 늘지 않고, 기존 세션은 끊기지 않습니다(프로필이 하나라 고르지 않아도 그 프로필로 씀). 되돌리려면 `restore pre-migration-...db`를 씁니다. 프로필이 없던 백업을 복구해도 복구 과정에서 같은 마이그레이션이 다시 돕니다.

## 복구 절차

1. **서버를 끕니다.** 켜 둔 채 복구해도 파일은 깨지지 않지만, 복구 중에 들어온 쓰기는 사라집니다.
2. `list`로 복구할 시점을 고르고 `verify`로 확인합니다.
3. `restore`를 실행합니다. 결과에 복구 전 DB 위치, 다시 지운 계정 수, 끝낸 세션 수, 비공개로 돌린 산책길 수가 나옵니다.
4. 서버를 켜고 `/api/health`와 로그인을 확인합니다.
5. 보호자에게 알립니다. 복구 시점 뒤의 기록이 사라졌고, 다시 로그인해야 하며, 공유는 다시 켜야 합니다.

잘못 복구했으면 결과에 나온 `pre-restore-*.db`로 다시 복구합니다. 지금 DB가 깨져 복사할 수 없으면 파일을 그대로 그 이름으로 옮겨 둡니다.

## 복구하면 달라지는 것

백업은 과거의 상태이므로, 그대로 되돌리면 사용자가 이미 없앤 것이 되살아납니다. 복구할 때 아래를 처리합니다.

| 항목 | 처리 | 이유 |
|---|---|---|
| 탈퇴한 계정 | 탈퇴 기록(`deletions.jsonl`)으로 다시 지움 | 탈퇴한 보호자가 되살아나면 안 됨 |
| 로그인 세션 | 모두 끝냄 | 백업 뒤에 로그아웃한 세션이 다시 열리면 안 됨 |
| 공유 링크, 공개 산책길, 커뮤니티 공개 | 모두 비공개로 돌림 | 백업 뒤에 해제한 공유를 구분할 수 없음. 위치 정보라 닫는 쪽을 택함 |
| 백업 뒤의 변경 | 사라짐 | RPO 범위 |
| 옛날 백업의 스키마 | 새 컬럼과 테이블을 더함 | 옛 백업도 지금 코드로 바로 씀 |

복구는 준비를 마친 임시 사본으로 지금 DB를 트랜잭션으로 덮어씁니다. 백업 파일은 바꾸지 않고, 백업이 손상되었으면 지금 DB에 손대기 전에 멈춥니다.

## 탈퇴와 백업

- 탈퇴하면 서비스 DB에서 바로 지우고, 지운 행은 파일에서도 0으로 덮어씁니다(`PRAGMA secure_delete`).
- 이미 만든 백업에는 보존 기간까지 남습니다. 탈퇴 화면에서 이 기간을 알립니다.
- `deletions.jsonl`에는 보호자 번호, 가입 시각, 탈퇴 시각만 있고 아이디, 이름, 이메일은 없습니다. SQLite는 지운 번호를 다시 쓸 수 있어, 같은 번호의 새 계정을 지우지 않도록 가입 시각으로 구분합니다. 복구에 필요하므로 보존 기간이 지나도 지우지 않습니다.
- 기록을 남길 수 없으면 탈퇴를 취소하고 다시 시도하도록 안내합니다. 기록 없이 지우면 복구 때 되살아나기 때문입니다.

## 한계

- **디스크 장애:** 기본 위치는 DB와 같은 디스크라 디스크가 망가지면 함께 사라집니다. `BACKUP_DIR`을 다른 디스크로 지정하세요. 원격 복사는 구현하지 않았습니다. 다른 곳으로 복사할 때는 `.sha256`과 `deletions.jsonl`도 함께 복사하세요.
- **암호화:** 백업 파일은 암호화하지 않고 권한으로만 막습니다. 밖으로 복사하면 암호화가 필요합니다.
- **탈퇴 기록 분실:** `deletions.jsonl`을 잃으면 복구 때 탈퇴한 계정이 되살아납니다. 복구 결과에 `탈퇴 기록 파일 없음`으로 표시합니다.
- **개별 삭제:** 기록을 남기는 것은 탈퇴뿐입니다. 탈퇴하지 않고 지운 산책길이나 사진은 백업 시점으로 복구하면 돌아옵니다.
- **보존 기간 지연:** 서버가 꺼져 있으면 백업도 정리도 멈추고, 켜면 바로 합니다. 백업이 계속 실패하면 복구 수단을 지키려고 옛 백업을 지우지 않으므로 14일을 넘길 수 있습니다.

## PostgreSQL

자동 백업과 복구 명령은 SQLite만 지원합니다. `DATABASE_URL`이 PostgreSQL이면 자동 백업을 건너뛰고 로그로 알리며, 명령은 이유를 알리고 멈춥니다. 탈퇴 화면에서도 백업 보존 기간을 말하지 않습니다.

PostgreSQL로 운영하면 `pg_dump` 같은 DB 도구로 백업하고, 복구 뒤 위 표의 처리와 `deletions.jsonl` 재적용을 직접 해야 합니다. 실제 연결부터 검증하지 않았습니다.

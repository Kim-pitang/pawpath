# 산책 경로 자동 생성 설계와 체크리스트

브랜치: `feature/generate-route`. 기존 코스에서 고르는 대신, 출발점과 원하는 산책 시간으로 순환 경로를 새로 만든다.
근거 데이터: `experiments/generated-walks/` (공용 OSRM 실측 52회, 12개 조건).

## 1. 실측에서 얻은 제약 (설계의 출발점)

| 관측 | 설계 반영 |
|---|---|
| 한 번의 OSRM 요청에 경유점 4개(출발-A-B-출발)를 넣어 순환 경로가 나옴, 응답 약 1초 | 후보당 요청 1회. 구간별 호출 금지 |
| 공용 서버 정책: 초당 1회, 대량 사용 금지 | 요청 간 1.1초 간격, 생성 1건당 8~11회(8방위 전부 + 후보가 모자랄 때만 보정 ≤3), 전체 30초, 동시에 한 건만 처리 |
| 목표 10분은 4개 지역 중 3곳에서 통과 후보 0개, 30분은 3곳(한강변 0, 개포동 1, 성미산 1)에서 1개 이하. **20분·90분은 실측하지 않았음(미검증)** | 하한 20분은 외삽값. 품질 기준을 못 넘기면 억지로 내놓지 않고 "만들지 못함" 반환. 한강변 같은 곳에서는 이 응답이 흔하다는 전제로 화면을 만든다 |
| 강변·개포동에서 왕복(반복 50%)과 목표 이탈이 흔함 | 반복 비율과 시간 오차로 걸러냄. 걸러진 결과만 노출 |
| 서버 장애·타임아웃 가능 | 실패는 명시 오류(502 성격)로 알리고 임의 직선 대체 없음 |

통과 기준: 시간 −20%~+50%, 반복 ≤25%, 출발점·경유점 도로 보정 ≤150m, 복귀 오차 ≤5m, 후보 간 겹침 ≤65%. 수치는 업계 표준이 아니라 우리가 정한 값이다.

**기준 변경 기록(2026-10-31):** 처음에는 실험 값 그대로(시간 ±20%, 보정 30m/75m)였으나, 개포디지털혁신파크 안에서 출발하니 가장 가까운 보행로까지 59.9m라 모든 후보가 탈락했다. 시간은 긴 쪽을 +50%까지, 보정은 150m까지로 완화했다. 150m, +50%는 근거 데이터 없이 정한 값이라 실사용으로 조정이 필요하다.

## 2. 구조

```
POST /api/routes/generate   (로그인 필요)
  body: latitude, longitude, duration_min (20~90)
  → route_generator.generate(origin, target_m, router)
       8방위(45° 간격) 전부 → 5개 미만이면 보정 ≤3회  (8~11요청)
       → 지표 계산 → 통과 후보 → 다양성 선택 ≤ 5개
  → (pet_id가 있으면) route_fit_service.fit_candidates          ← 4장
       미리 수집한 OSM 자료로 후보별 환경 측정 → CourseData → 기존 추천 엔진 → 점수 순 정렬
  resp: candidates[{route, distance_m, duration_min, repeated_pct, start_snap_m, fit}], target, notice, scored_for, fit_notice

저장: 기존 POST /api/my-walks  (source_type="generated", 신규 엔드포인트 없음)
추천 후보 등록: 기존 POST /api/my-walks/{id}/course  (register())
```

- 라우터: 기존 2점 `route()`는 그대로 두고 다중 경유점 `route_via(points)`를 추가한다. 응답의 `waypoints[].distance`(도로 보정 거리)를 함께 돌려준다.
- 공용 서버 보호: 프로세스 전역 락(non-blocking, try/finally 해제)으로 동시에 한 건만 처리하고 진행 중이면 429. 계정 하나가 락을 반복 점유하지 못하도록 사용자별 대기 시간(완료 후 10초)을 둔다. 생성 1건의 전체 제한 시간은 30초. 한계: 락은 프로세스 단위라 워커가 여러 개면 전역이 아니고, `/routes/walking`·`/courses/{id}/approach`는 같은 공용 서버를 쓰지만 이 락 밖이다(워커 1개·시연 규모 전제).
- 좌표는 계산에만 쓰고 로그·DB에 남기지 않는다(저장은 사용자가 후보를 골라 저장할 때만).
- 출발점: 현재 위치 또는 지도에서 지정.
- 저장 시 `source_type="generated"`는 클라이언트가 보내는 자기 신고 값이며 서버가 경로의 출처를 검증하지 않는다(GPX·기록도 동일). 점 개수는 기존 상한(10만)을 따른다.
- 개인화: 이번 범위에서는 시간(일정·반려동물의 선호 시간)만 입력으로 쓴다. 성향·경로 선호로 경로를 고르는 것은 하지 않는다. 저장 후 추천 후보로 등록하면 기존 추천 엔진이 반려동물 맞춤 점수를 계산한다.

## 2-1. 자체 OSRM 전환 대비 (사용자 계획)

나중에 OSRM을 직접 띄울 예정이라, 공용 서버용 제한값을 코드에 박지 않고 설정으로 뺐다.
`ROUTING_BASE_URL`을 자체 서버로 바꾸고 `ROUTING_MIN_INTERVAL_SECONDS=0`, `GENERATION_COOLDOWN_SECONDS`를 줄이면 코드 수정 없이 전환된다.
탐색 범위도 설정으로 뺐다(기본값은 공용 서버용이라 동작이 그대로다): `GENERATION_BEARINGS`(방위 수), `GENERATION_RADIUS_SCALES`(경유점 거리 배율), `GENERATION_SPREADS`(경유점 벌어짐 각도), `GENERATION_MAX_REQUESTS`, `GENERATION_POOL_SIZE`(평가 전 후보 수), `GENERATION_MAX_RESULTS`(화면에 줄 수).
시도 수는 방위 × 배율 × 각도(요청 상한까지)이고, 반려동물을 주면 pool만큼 만들어 엔진 점수로 평가한 뒤 점수 높은 순으로 max_results개만 돌려준다. 시도를 늘리면 `GENERATION_MAX_SECONDS`도 함께 올려야 한다(기본 30초는 간격 1.1초에서 요청 약 27회). 동시 1건 제한(`GenerationGate`)은 아직 코드 구조 그대로다.
**로컬 OSRM 실측(2026-10-31, `127.0.0.1:5001` 서울 추출본, 30분, 데모 반려견):** 요청 한 번 약 5ms(공용 서버 약 1초). 144요청(방위 24 × 배율 3 × 각도 2)이 0.6초.
서로 다른 통과 후보는 망원동 8(8방위) → 26(48요청) → 50 이상(144요청, 상한에 걸림), 개포디지털혁신파크 2 → 6 → 8.
후보를 늘린 효과는 장소마다 달랐다: 개포는 최고 점수가 70.7 → 73.3(공원을 지나고 큰 도로변이 66% → 28%인 후보를 새로 찾음), 망원동은 최고 점수 75.3 그대로(상위 5개가 74.6~75.3으로 촘촘).
점수 상위 5개끼리의 겹침은 평균 18~31%, 최대 61%로 비슷한 경로만 모이지는 않았다.
병목은 요청이 아니라 **평가 시간**이다: 후보 50개 평가 3.3초, 풀 30개 기준 API 전체가 30분 1~3초, 60분 7~10초. 환경 측정이 경로 길이 × 주변 요소 수에 비례하기 때문이다(최적화는 안 함). 90분은 측정하지 않았다.

## 3. 지금 안 하는 것 (결정)

- GraphHopper/ORS 등 전용 라운드트립 엔진 (운영 비용 대비 과함)
- 경유점을 공원·수변 POI로 고르기, 보행 가능 도로에 스냅하기(nearest API 추가 호출)
- 결과 캐시, 사용자별 호출 제한, 자체 OSRM 서버
- 경로 품질을 학습하는 ML 모델(산책 기록·피드백이 모자라 학습 데이터가 없음). 추천 엔진에 순위 모델 교체 지점(`Ranker`)이 이미 있으니 데이터가 쌓이면 그때 검토
- LLM이 경로나 좌표를 만들거나 순위를 정하게 하는 것(좌표 환각, 비용·지연, 결과가 매번 달라짐). 설명 문장은 기존 `explain`(템플릿, 선택적 LLM)을 그대로 씀
- 짧은 가지 구간 감점 (반복 지표로 일부만 간접 대응)

## 5. 경로 평가 고도화 (2026-10-31 추가)

목표: 시간만 맞는 경로가 아니라 "이 반려견이 이 시간에 걷기 좋은 길인지"를 근거와 함께 판단한다.

### 5-1. 설계 결정
- **새 점수 체계를 만들지 않는다.** 저장한 산책길을 추천 후보로 등록할 때(`user_course_service`)와 같은 변환으로 후보를 `CourseData`로 만들고 기존 추천 엔진(`recommend`)에 넣는다. 반려견 성향·활동량·날씨·일정·지난 피드백 학습·안전 평가·설명 문장이 그대로 적용된다. 후보 번호는 음수로 두어 저장된 코스의 학습 기록과 섞이지 않는다. `recommend()`에는 `top_n` 인자만 추가했다.
- 이번 산책 시간은 사용자가 슬라이더로 고른 값이라, 일정에 적어 둔 평소 희망 시간 대신 이 값으로 시간 적합도를 계산한다.
- 측정하지 못한 값은 중립값으로 계산하고 `unknown`에 남기며 안전하다고 보지 않는다(저장 코스와 같은 원칙).

### 5-2. 실측으로 바뀐 결정: 요청 시점 Overpass를 쓰지 않는다
처음에는 후보를 덮는 영역을 요청마다 공용 Overpass로 받아 측정하게 만들었다. 실제로 돌려 보니
`overpass-api.de`는 아주 작은 쿼리에도 타임아웃, `maps.mail.ru`는 작은 쿼리에 504였고 망원동 1.2km 상자의 도로 쿼리 하나에 28.8초가 걸렸다.
환경 측정이 실패하면 후보 5개 점수가 71~72점대로 거의 같아져 순위가 의미가 없었다. 그래서:
- 서비스 지역(망원동·개포동) 중심에서 반경 약 3km 상자의 도로·나무·공원을 `scripts/collect_osm_area.py`로 미리 받아 `backend/app/data/osm_<지역>.json`으로 둔다(시설을 `places*.json`으로 두는 것과 같은 방식). 서버는 파일만 읽으므로 평가가 외부 서비스에 의존하지 않는다.
- 자료가 덮지 않는 곳(서비스 지역 밖)의 경로는 측정하지 않고 '확인 불가'로 둔다. 추측하지 않는다.
- 받은 자료의 날짜(`collected_on`)를 결과에 적는다. 길이 바뀌어도 자동 갱신되지 않으므로 필요하면 스크립트를 다시 돌린다.
- 한 조각이라도 못 받으면 파일을 쓰지 않는다(빠진 길이 "길 없음"으로 읽히는 것을 막기 위해).

### 5-3. 지금 안 하는 것 (이번 단계의 결정)
- 경사·반려견 출입은 여전히 평가하지 않는다(자료 없음).
- "혐오 시설"은 따로 분류하지 않는다. OSM 태그로 대신할 수 있는 큰 도로변 비율·조명·노면만 이미 엔진이 쓰고 있다. 정의가 정해지면 `FACILITY_TYPES`/수집 질의를 늘리는 방식으로 추가한다.
- 서비스 지역 밖은 자료를 받지 않는다. 자체 OSRM과 서울 추출본을 띄우게 되면 같은 추출본에서 도로·나무·공원을 뽑는 쪽이 일관적이다.
